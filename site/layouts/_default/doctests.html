Docs tests

These tests read the docs the way a developer would, code and text alike. Every code sample runs against a mock of the API. Every claim in the text, such as "this endpoint exists" or "retrying is safe", is checked against the API's spec. When the next release arrives, they show what it breaks, before your customers do.

How the tests work

The tests read each page's Markdown file. Every curl sample runs as written against a mock of the API, so a sample that's wrong for the spec, fails here before a user runs it. The text around the samples is checked as well, for example: how long idempotency keys are kept, the webhook time window or the latest version.

TestWhat it checks
Endpoints exist in the specEvery curl sample calls an endpoint that's in the spec.
Authentication matches the specSamples send a Bearer token in the Authorization header.
Parameters and headers match the specEvery field and query parameter is in the spec, required ones are there, values have the right type and are within limits, and required headers such as Idempotency-Key are sent.
Sample runs against the mock APIThe sample, run as written, gets a successful response from the mock.
Retrying after a timeout is safeThe page says to retry with the same Idempotency-Key, and sending its sample twice creates one payment, not two. If the page says how long keys are kept, a retry just before that time ends must still create only one payment.
Signature header and rules match the specThe webhooks page names the header, the algorithm and the time window that the spec gives.
Latest release matches the specThe changelog's latest entry is the version in the spec.

The API reference pages aren't tested here because they're generated from the spec. The Before docs aren't tested either: they're HTML pages that were never kept as code, so there's nothing to test them with.
