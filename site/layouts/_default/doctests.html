Docs tests

Every page of the docs gives guidance you can check: this endpoint exists, this sample works, retrying is safe. These tests check that guidance against the OpenAPI spec and against a mock of the API built from it. When the next release's spec arrives, the same tests show the docs team what it breaks, before it ships.

How the tests work

The tests read each page's Markdown file, the same file the site publishes. Every curl sample is run as written against a mock of the API that knows only what the spec says, so a sample that's wrong for the spec fails here before a reader runs it. The text around the samples is checked as well: each value the page states, such as how long idempotency keys are kept, the webhook time window or the latest version, is compared with the spec.

TestWhat it checks
Endpoints exist in the specEvery curl sample calls an endpoint that's in the spec.
Authentication matches the specSamples send a Bearer token in the Authorization header, never ?api_key= in the URL.
Parameters and headers match the specEvery field and query parameter is in the spec, required ones are there, values have the right type and are within limits, and required headers such as Idempotency-Key are sent.
Sample runs against the mock APIThe sample, run as written, gets a successful response from the mock.
Retrying after a timeout is safeThe page tells you to retry with the same Idempotency-Key, and sending its sample twice creates one payment, not two. If the page says how long keys are kept, the mock retries again a minute before that time is up, with keys expiring when the spec says, and it must still be one payment.
Signature header and rules match the specThe webhooks page names the header, the algorithm and the time window that the spec gives.
Latest release matches the specThe changelog's latest entry is the version in the spec.

When the next release arrives

The spec reaches the docs team before the release does. The tests turn it into a list of what to fix, and the same steps run on a laptop and on GitHub.

  1. A new spec is ready for review. When the next release's spec is ready, we run the same tests on the same docs against it.
  2. The tests run against both specs. The tests, the mock API and the unreleased spec live in a private repository, which holds the docs too: only the docs and the site are published. In VS Code: python tests/run_doc_tests.py there. On GitHub: a workflow in that repository runs the same command whenever the incoming spec or the tests change. The table above shows the result: each failure in the incoming column names the file, the line and the reason.
  3. Claude drafts the fix. In VS Code, ask Claude Code to /fix-docs. On GitHub, the workflow asks Claude to follow the same instructions and opens a pull request with the fix in the private repository, so nothing about the release is public before it ships. Claude compares the two specs, fixes the failing lines and anything else the release makes wrong, adds the changelog entry, and runs the tests until the incoming column passes.
  4. A human reviews the fix, and the release ships with its docs. Once the pull request is approved and merged, the incoming spec moves to the docs' specs/ folder and the docs and the site are pushed to the public repository. The spec becomes the current release, and the site publishes it and the updated docs together.
